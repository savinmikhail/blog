# Практический гайд по env: файлы, приоритеты, кеширование и секреты

Сколько работаю с конфигурацией, столько из неё вылезают сюрпризы. Поменял пароль — приложение использует старый. Добавил `env_file` — Compose продолжает жаловаться на отсутствующую переменную. Убрал файл из Git — ключ обнаружился в логе. А файл, который вчера успешно читал один инструмент, сегодня иначе разобрал другой.

Здесь я собрал способы организовать настройки, понять итоговое значение и не раскрыть секрет во время отладки. Основные примеры — PHP и Docker Compose. Когда поведение зависит от загрузчика, это будет указано: соглашение Symfony нельзя автоматически переносить на Laravel или Node.

В конце есть [запускаемый пример](example/README.md) и таблица поиска неисправностей. Все credentials в примерах искусственные.

## 1. Что такое env и кто его читает

Под env часто подразумевают сразу несколько разных вещей:

| Слой | Что это | Кто работает с ним |
|---|---|---|
| Окружение процесса | Переданные процессу строковые значения | ОС, рантайм, дочерние процессы |
| `.env` | Текстовый файл с настройками | Конкретный загрузчик |
| Конфигурация приложения | Значения после загрузки, преобразований и проверки | Код приложения |
| Дамп или кеш | Ранее вычисленный результат | Bootstrap, фреймворк, воркер |

Файл не экспортирует себя в окружение. Кто-то должен его прочитать: Compose, библиотека, фреймворк или shell. И результат тоже разный: загрузчик может заполнить структуру данных PHP, окружение процесса либо модель Compose.

Например, `$_ENV`, `$_SERVER` и `getenv()` в PHP нельзя безусловно считать одним хранилищем. Результат зависит от конфигурации PHP, SAPI и способа загрузки. Используйте один предусмотренный приложением интерфейс конфигурации, а не ищите значение по очереди во всех возможных местах. [PHP getenv](https://www.php.net/manual/en/function.getenv.php), [phpdotenv](https://github.com/phpdotenv/phpdotenv).

Окружение наследуется при запуске дочернего процесса. Оно не является общей изменяемой памятью: изменение переменной в одном shell не обновляет уже работающий воркер или другой терминал.

Полезный вопрос для любой настройки: **кто её задаёт, кто читает, в какой момент и кому ещё она становится доступна?**

## 2. Как организовать конфигурацию проекта

Один `.env` легко превращается в смесь портов Compose, паролей БД, feature flags, ключей внешних API и настроек мониторинга. Начать можно с разделения ответственности:

```text
.env                  # несекретные настройки инфраструктуры
.env.local            # локальные инфраструктурные overrides
app/.env              # общие настройки приложения
app/.env.local        # локальные настройки и секреты приложения
```

Порт, публикуемый Compose, не обязан становиться переменной PHP. Токен внешнего API не нужен nginx. При этом разделение файлов не создаёт передачу данных: если приложение собирает DSN из инфраструктурных параметров, нужно явно передать нужные компоненты или готовый DSN.

### Что коммитить

Решение зависит от содержимого и соглашений загрузчика. В Symfony общие `.env` и environment-specific файлы коммитятся, local overrides — нет. В Laravel принят `.env.example`, а рабочий `.env` исключается из Git. [Symfony](https://symfony.com/doc/current/configuration.html#overriding-environment-values-via-env-local), [Laravel](https://laravel.com/docs/12.x/configuration#environment-configuration).

Я бы оценивал не расширение, а каждую настройку:

| Значение | Пример | Хранение в Git |
|---|---|---|
| Общий несекретный default | `LOG_LEVEL=info` | Обычно допустимо |
| Локальный выбор | Свободный порт разработчика | Local override |
| Безопасные тестовые данные | Пароль изолированной одноразовой БД | Допустимо при явной границе |
| Настоящие credentials | Production API token | Отдельный защищённый канал |

Placeholder вроде `change-me` не является безопасным production-паролем. Деплой должен отказаться продолжать, пока обязательный секрет не задан.

Для большого файла помогают группы с комментариями и краткое описание назначения. Для `.env.example` полезна проверка обязательных ключей в CI: пример должен помогать запустить проект, а не быть снимком годичной давности. Не генерируйте его копированием текущих значений из production.

В CI можно хранить приватный файл через механизм file variables и доставлять его при деплое. Планируйте владельца/права, время жизни временного файла и путь передачи; не печатайте содержимое через `echo`, shell trace или общий debug-артефакт. File variable даёт скрипту путь к файлу, а не запрет чтения. [GitLab variables](https://docs.gitlab.com/ci/variables/).

## 3. Приоритеты: какое значение победит

Универсального порядка для всех инструментов нет. Важно отдельно выяснить порядок **источников** и момент **вычисления**.

| Загрузчик | Характерное поведение |
|---|---|
| Symfony стандартный bootstrap | `.env` → `.env.local` → `.env.<environment>` → `.env.<environment>.local`; внешние значения обычно сохраняются; в test `.env.local` пропускается |
| Laravel | Внешние значения перекрывают файл; выбор `.env.<environment>` и кеш имеют отдельные правила |
| Node `--env-file` | Внешнее окружение выше; поздний файл перекрывает ранний |
| python-dotenv | Существующие env сохраняются по умолчанию; `override=True` меняет поведение |

Здесь стрелки относятся только к стандартной загрузке файлов Symfony, а не ко всему жизненному циклу приложения. Настройки bootstrap могут менять правила. Источники: [Symfony](https://symfony.com/doc/current/configuration.html#overriding-environment-values-via-env-local), [Laravel](https://laravel.com/docs/12.x/configuration#environment-configuration), [Node CLI](https://nodejs.org/api/cli.html#--env-filefile), [python-dotenv](https://bbc2.github.io/python-dotenv/).

Не переносите правило «последний файл побеждает» на другую библиотеку. И проверяйте, что она делает с пустым значением: это может быть явный override, а не сигнал искать default.

### Производное значение не обязано пересчитываться

Допустим, один файл содержит:

```dotenv
DB_HOST=localhost
DB_PORT=5432
DATABASE_URL="postgresql://${DB_HOST}:${DB_PORT}/app"
```

Позже загружается файл с `DB_HOST=db`. Если первый загрузчик уже раскрыл `DATABASE_URL` в строку, объединение значений само по себе не пересоберёт её. Это надо проверять у конкретного загрузчика. В [опыте с Symfony Dotenv 7.4.18](example/dotenv-probe.php) `loadEnv()` как раз пересчитал зависимый URL с local host. Это поведение нельзя обобщать на все загрузчики. Например, отдельно прочитанные через `dotenv_values()` Python-файлы уже интерполированы до объединения словарей. [python-dotenv](https://bbc2.github.io/python-dotenv/).

Для критичных составных настроек удобно выбрать одно место сборки: сначала получить и проверить компоненты, затем собрать DSN. Либо передавать готовый DSN как самостоятельное значение и не создавать иллюзию связи с отдельными `DB_*`.

## 4. Синтаксис, интерполяция и спецсимволы

Node прямо отмечает отсутствие единой формальной спецификации dotenv и определяет собственные правила. Поэтому совместимость файла нужно проверять для реальных потребителей. [Node Environment Variables](https://nodejs.org/api/environment_variables.html).

Я прогнал один искусственный файл через несколько инструментов:

```dotenv
BASE=alpha
EXPANDED=${BASE}/data
LITERAL=cost$$cash
```

| Обработчик | EXPANDED | LITERAL |
|---|---|---|
| Node `--env-file` | `${BASE}/data` | `cost$$cash` |
| Bash `source` | `alpha/data` | `cost<PID>cash` |
| Make `include` с export | `alpha/data` | `cost$cash` |
| Compose `config --format json` | `alpha/data` | `cost$$cash` |

[Скрипт и результаты](experiments/README.md) привязаны к версиям. Последняя строка — сериализованная модель Compose, а не наблюдение окружения контейнера: вывод может экранировать `$`. Bash и Make здесь показаны потому, что ими нередко подключают настройки, хотя оба читают собственные языки.

Для обычного `.env` Compose несколько конкретных правил выглядят так:

| Запись | Результат |
|---|---|
| `BASE=alpha` и `VALUE="${BASE}/data"` | `alpha/data` |
| `VALUE='${BASE}/data'` | Буквальная `${BASE}/data` |
| `VALUE=hello # comment` | `hello` |
| `VALUE=hello#world` | `hello#world` |
| `VALUE="hello # world"` | `hello # world` |
| `VALUE=` | Пустая строка |

Двойные кавычки поддерживают escape-последовательности вроде `\n`, одинарные сохраняют их буквально; одинарно заключённое значение Compose может занимать несколько строк. [Compose syntax](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax).

Это правила выбранного парсера. Перед переносом в Symfony/Node/Make проверяйте тот же fixture, включая буквальный backslash и пробелы. Не применяйте shell-экранирование к dotenv автоматически.

### Пароль в DSN проходит два разных парсера

Сначала dotenv разбирает строку, потом клиент БД разбирает URL. Правильные кавычки в `.env` не делают `?`, `@` или `#` безопасными внутри URL-компонента.

Если DSN собирается в PHP, кодирование применяется к отдельным компонентам:

```php
$user = rawurlencode($dbUser);
$password = rawurlencode($dbPassword);
$dsn = "postgresql://{$user}:{$password}@{$dbHost}:{$dbPort}/{$dbName}";
```

Это фрагмент для заранее проверенных host, port и имени БД, не универсальный DSN-builder. Не кодируйте целиком готовый URL и не кодируйте пароль повторно. [PHP rawurlencode](https://www.php.net/manual/en/function.rawurlencode.php). Для конкретного драйвера сверяйте поддерживаемый синтаксис; при наличии API отдельных полей он может быть проще.

PEM-ключи и другие многострочные секреты часто удобнее доставлять файлом: это убирает один слой кавычек и экранирования.

## 5. Env в Docker и Compose

Самая частая путаница — считать `.env` Compose и `env_file` сервиса одним механизмом.

### Стадия A: Compose строит модель

```dotenv
# .env
APP_HTTP_PORT=8080
```

```yaml
services:
  app:
    image: example/app
    ports:
      - "${APP_HTTP_PORT}:80"
```

Значение участвует в интерполяции YAML. Это ещё не означает, что `APP_HTTP_PORT` есть в окружении приложения.

Compose может брать значения из shell и выбранных env-файлов. При нескольких `--env-file` поздний файл перекрывает ранний, но shell остаётся важным внешним источником. Пути и рабочая директория влияют на поиск файлов. [Compose interpolation](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

```bash
docker compose --env-file .env --env-file .env.local config
```

Здесь оба файла должны существовать. Для команды-обёртки не нужно делать `source`: передайте пути самому Compose. Альтернативный механизм:

```bash
export COMPOSE_ENV_FILES=.env,.env.local
docker compose config
```

Обычное присваивание shell-переменной без export не передаёт её дочерней команде.

### Стадия B: задаётся окружение сервиса

```yaml
services:
  app:
    image: example/app
    env_file:
      - path: ./app/.env
        required: true
      - path: ./app/.env.local
        required: false
    environment:
      APP_ENV: prod
```

Service `env_file` задаёт окружение контейнера, а не источник подстановки `${...}` в YAML. `environment` перекрывает `env_file`, включая явно пустые значения. `required: false` требует Compose 2.24+, `format: raw` — 2.30+; raw управляет разбором значений, но не маскирует их. [Services reference](https://docs.docker.com/reference/compose-file/services/#env_file).

Для контейнерного окружения отдельно сравниваются `run -e`, `environment`, `env_file` и image `ENV`. Не превращайте это в общую таблицу вместе с приоритетом файлов внутри PHP. [Container environment precedence](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/).

### Сборка и запуск

`ARG` относится к сборке образа, `ENV` может задавать defaults окружения в образе. Настройки приложения, вычисленные при сборке, не обязаны измениться от новых runtime env. Особенно заметно это во frontend: собранный JS уже содержит подставленные значения.

Credentials для скачивания приватных зависимостей передавайте через build secrets, а не записывайте в `ARG`, `ENV` или скопированный файл образа. [Docker build secrets](https://docs.docker.com/build/building/secrets/).

## 6. Кеширование и обновление конфигурации

Фраза «почисти кеш» скрывает несколько разных операций. Сначала выясните, что именно хранит старое значение.

### Symfony

`composer dump-env prod` создаёт `.env.local.php`; стандартный bootstrap может загружать этот дамп вместо текстовых файлов. После изменения исходников dotenv нужно пересоздать дамп. Это отдельный артефакт, не синоним кеша DI-контейнера. Реальные переменные окружения и настройки bootstrap продолжают иметь значение. [Symfony dotenv production](https://symfony.com/doc/current/configuration.html#configuring-environment-variables-in-production).

```bash
composer dump-env prod
APP_ENV=prod APP_DEBUG=0 php bin/console cache:clear
```

Команды относятся к разным слоям и выполняются в подготовленном окружении деплоя. Обычные `%env(...)%` и значения, намеренно разрешённые при компиляции контейнера, также различаются по моменту чтения. Поэтому изменение env не всегда требует очистки DI-кеша. [Env processors и compile-time resolution](https://symfony.com/doc/current/configuration/env_var_processors.html#resolving-environment-variable-at-compile-time), [Deployment](https://symfony.com/doc/current/deployment.html).

### Laravel

`php artisan config:cache` сохраняет вычисленную конфигурацию. После этого `.env` не загружается для запросов и Artisan, а `env()` видит только внешние переменные. Поэтому `env()` вызывается в config-файлах, приложение использует `config()`; после изменения источников конфигурацию пересобирают. Для удаления кеша есть `config:clear`. [Laravel configuration caching](https://laravel.com/docs/12.x/configuration#configuration-caching).

### Процессы и внешнее состояние

Queue workers живут долго и сохраняют загруженное состояние. Для Laravel предусмотрен `queue:restart`; нужен процесс-менеджер, который запустит завершившиеся воркеры заново. [Queue deployment](https://laravel.com/framework/docs/12.x/queues#queue-workers-and-deployment).

| Что изменили | Какое действие проверить |
|---|---|
| Symfony dotenv при наличии дампа | Пересоздать `.env.local.php` |
| Laravel config/env при активном config cache | Пересобрать config cache |
| Окружение контейнера в Compose | Пересоздать затронутый контейнер; [простой restart](https://docs.docker.com/reference/cli/docker/compose/restart/) не применяет новую спецификацию |
| Конфигурацию долгоживущего процесса | Предусмотренный reload/restart |
| Файл секрета | Проверить доставку обновления и перечитывание приложением |
| Frontend build-time значение | Пересобрать и доставить bundle |

И ещё один отдельный слой: состояние самой БД. У официального Postgres-образа init-переменные применяются при первоначальной инициализации пустого каталога данных. Новое `POSTGRES_PASSWORD` не меняет пароль существующей роли в уже инициализированной БД. Для ротации нужна операция изменения credentials и согласованное обновление клиентов. Удаление volume ради применения env уничтожит данные. [Postgres image](https://github.com/docker-library/docs/tree/master/postgres#environment-variables).

## 7. Типы, defaults и валидация

Строка `false` не обязана означать boolean false. Например, в PHP прямой `(bool) 'false'` даёт true. У фреймворка может быть свой преобразователь, а у приложения — более строгий контракт.

В Symfony есть processors `int:`, `bool:`, `json:`, `file:` и другие. Они преобразуют значение; требования вроде «порт от 1 до 65535» или «этот параметр обязателен только при включённой интеграции» приложение проверяет отдельно. `resolve:` раскрывает `%parameter%` Symfony, а не является общим механизмом `${VARIABLE}` dotenv. [Processors](https://symfony.com/doc/current/configuration/env_var_processors.html).

Минимальный контракт настройки:

| Поле | Пример |
|---|---|
| Имя и назначение | `DB_PORT`, порт БД для приложения |
| Тип и ограничения | integer, 1..65535 |
| Обязательность/default | Обязателен или default 5432 |
| Чувствительность | Public/secret по явному правилу |
| Потребитель | Только приложение |
| Обновление | При запуске / явный reload |

Для важного boolean можно принять только `true` и `false`, отвергая опечатки. Отсутствие значения, пустая строка и допустимый ноль проверяются отдельно: универсальная проверка `if (!$value)` смешивает их.

Проверки полезно разделить по слоям:

| Слой | Что проверяет | Где применять |
|---|---|---|
| Linter | Правила синтаксиса и оформления выбранного dialect | Локально и CI |
| Compose config | Разрешение модели и подстановок | Перед запуском; вывод считать потенциально секретным |
| Runtime schema | Итоговые типы, диапазоны и зависимости | При старте приложения |
| Production guard | Обязательные секреты и запрещённые defaults | Перед переключением трафика |
| Secret scanner | Известные признаки credentials в файлах/истории | Pre-commit и CI |

Каждый слой проверяет своё; успешный linter не означает, что процесс получил правильное значение. [dotenv-linter](https://github.com/dotenv-linter/dotenv-linter) и [Gitleaks](https://github.com/gitleaks/gitleaks) решают разные задачи; ни один не доказывает корректность всего runtime. В CI проверяйте и актуальное дерево, и историю по выбранной политике; найденный секрет требует отзыва, а не только удаления строки.

Production guard должен отклонять отсутствующие секреты и известные placeholders. Это не проверка качества любого пароля: `admin123` может пройти такой guard. Для собственных токенов используйте криптографический генератор, например `bin2hex(random_bytes(32))`, и сохраняйте результат напрямую в защищённое место без печати в CI-лог. [PHP random_bytes](https://www.php.net/manual/en/function.random-bytes.php).

Проверка при старте даёт короткую ошибку `DB_PORT: integer in range 1..65535 required`, а не стек с полным DSN.

## 8. Когда конфигурация становится исполняемым кодом

```dotenv
VALUE=$(printf synthetic-command-ran)
```

При `source .env` Bash выполнит `printf`. Встроенный Node `--env-file` в нашем [безопасном опыте](experiments/format-probe.py) оставил выражение строкой. Подмена `printf` произвольной командой меняет последствия, но не принцип: `source` исполняет shell-код с правами загрузившего его процесса.

Предпосылка атаки — возможность изменить файл, который затем загрузит доверенный процесс. Особенно внимательно относитесь к такому пути в deploy/CI/entrypoint. Расширение `.env` не ограничивает shell.

`Make include` читает make-синтаксис, в том числе функции; PHP/JS-конфиги также являются кодом. Даже специализированный loader может поддерживать исполнение. Symfony Dotenv 7.4.18 раскрывает `$()` на Unix при установленном Symfony Process; без него этот механизм выдаёт ошибку. Это видно в [resolveCommands()](https://github.com/symfony/dotenv/blob/v7.4.18/Dotenv.php). Dotenvx также документирует command substitution. Проверяйте возможности выбранного загрузчика, а не доверяйте имени формата. [dotenvx](https://github.com/dotenvx/dotenvx#readme).

Исполнение может возникнуть и через назначение переменной. Node применяет `NODE_OPTIONS` из `--env-file`, включая допустимые настройки preload. Это не значит, что любой `dotenv.config()` в уже работающем процессе перезапускает Node, но недоверенный startup env требует контроля. [Node CLI](https://nodejs.org/api/cli.html#--env-filefile).

**Два примера настоящих CVE:** npm JSON5 имел prototype pollution возвращаемого объекта, исправленную в 1.0.2/2.2.2; python-dotenv — перезапись файла через symlink при cross-device fallback операций `set_key`/`unset_key`, с указанным исправлением 1.2.2. Это разные дефекты конкретных реализаций с конкретными предпосылками, не «любой env приводит к RCE». [JSON5 advisory](https://github.com/json5/json5/security/advisories/GHSA-9c47-m6qq-7p4h), [python-dotenv advisory](https://github.com/theskumar/python-dotenv/security/advisories/GHSA-mf9w-mj56-hr94).

## 9. Секреты: хранение, доставка и права доступа

Секретность — свойство значения и его назначения. Не каждый параметр секретен, но даже hostname или идентификатор tenant может быть чувствительным в конкретной системе. Классифицируйте явно.

Передавать приложению настройки через env нормально, если это выбранный интерфейс. Автоматически экспортировать весь конфиг всем сервисам — лишнее распространение. Чтение файла внутри приложения может уменьшить распространение через окружение, но процесс с доступом к файлу всё равно способен прочитать секрет.

### Compose secrets

```yaml
services:
  app:
    image: example/app
    environment:
      APP_TOKEN_FILE: /run/secrets/app_token
    secrets:
      - app_token
secrets:
  app_token:
    file: ./secrets/app-token.txt
```

В env передаётся путь; приложение должно поддерживать чтение файла. Суффикс `_FILE` — соглашение потребителя, не автоматическая функция любого приложения. File-based Compose secrets не шифруют исходный файл на хосте; сервисы получают только явно назначенные secrets. Для источника `file` не рассчитывайте, что `uid/gid/mode` в YAML изменят права bind mount. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/), [Services reference](https://docs.docker.com/reference/compose-file/services/#secrets).

### Другие механизмы

Kubernetes разделяет ConfigMap и Secret. Secret не означает автоматического encryption at rest: нужны соответствующая настройка кластера и права. Env-значение в работающем Pod не обновляется от изменения объекта; файловая доставка имеет свои правила обновления, а приложение должно перечитать файл. [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/), [ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/).

SOPS позволяет хранить зашифрованные файлы, а secret manager — отдельно управлять доступом и выдачей. Дешифрование всё равно требует доверенного получателя и ключа. Выбор между ними зависит от нужных свойств: история версий, аудит, отзыв, срок жизни и доступность. [SOPS](https://github.com/getsops/sops).

`chmod 600` закрывает файл от других обычных пользователей, но оставляет доступ владельцу. Проверять нужно также права каталога, пользователя процесса, mounts и доступ к Docker daemon. Это один контроль, не полная граница безопасности.

## 10. Диагностика, маскирование и утечки

Диагностика часто раскрывает больше, чем само приложение. `env`, `printenv`, `phpinfo`, дамп `$_ENV`, конфигурационный debugger, `docker inspect` и resolved Compose config требуют осторожности. В нашем [опыте](experiments/leak-probe.py) `compose config` напечатал искусственный API key из `environment` открытым текстом.

Начинайте с метаданных:

```text
DB_PORT       present=yes  valid=yes  origin=process-at-bootstrap
APP_TOKEN     present=yes  valid=yes  transport=file
```

Происхождение не восстанавливается автоматически из готовой строки. Если loader его не сохранил, можно честно различать только ограниченные категории, например «было в процессе до bootstrap» и «добавлено dotenv». Полная цепочка файлов требует поддержки загрузчика или отдельного диагностического алгоритма. Не выдавайте догадку за provenance.

Значения показывайте только для явно разрешённых полей. Не выводите хеши секретов по умолчанию: для коротких значений это даёт возможность проверки догадок. Производные строки тоже чувствительны — маскирование `DB_PASSWORD` не гарантирует удаления того же пароля из кодированного DSN.

### Где ещё оказывается значение

- Debug-страница ошибки и profiler. Laravel отдельно предупреждает об опасности `APP_DEBUG=true` в production. [Laravel debug](https://laravel.com/docs/12.x/configuration#debug-mode).
- Кеш конфигурации и dotenv dump: защищайте их как исходные данные, не публикуйте через веб-сервер и общие артефакты. Исключайте приватные dotenv, дампы и каталог secrets из ненужного build context через `.dockerignore`: одного `.gitignore` для `COPY . .` недостаточно. [Docker build context](https://docs.docker.com/build/concepts/context/#dockerignore-files).
- Frontend bundle: значение, включённое в браузерный JS, доступно пользователю независимо от `.gitignore`. Vite прямо предупреждает не помещать секреты в `VITE_*`. [Vite env](https://vite.dev/guide/env-and-mode).
- CI: masking убирает некоторые совпадения из логов, но не запрещает скрипту читать или отправлять секрет. [GitLab variables](https://docs.gitlab.com/ci/variables/).

Маскирование полезно, когда его границы известны. Например, Spring Actuator по умолчанию скрывает значения диагностических endpoints; это не меняет доступ самого процесса к настройкам. [Spring sanitization](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.sanitization).

Если ключ уже раскрылся, удаление `.env` из Git не отзывает его. Отзовите/ротируйте credential, проверьте доступные логи использования, затем устраните канал и очистите доступные копии. Реальные кампании использовали публичные `.env` для получения облачных credentials. [Unit 42](https://unit42.paloaltonetworks.com/large-scale-cloud-extortion-operation/).

## 11. Работа с env при использовании LLM-агентов

Агент получает данные через инструменты. Поэтому вопрос не только «можно ли модели открыть `.env`», но и «какие инструменты вернут то же значение».

| Канал | Пример |
|---|---|
| Прямое чтение | Файл dotenv, дамп конфигурации |
| Shell | `cat`, `printenv`, собственный Python/PHP-скрипт |
| Диагностика | Compose config, profiler, сообщение ошибки |
| Дочерний процесс | Тесты с унаследованным env |
| Инфраструктура | Docker socket, secret manager CLI |

`.gitignore` не запрещает чтение, а `chmod 600` не отделяет агента от владельца. Запрет встроенному Read-инструменту также не доказывает, что произвольный subprocess не прочитает файл. Документация Claude Code отдельно описывает ограничения permissions и OS sandbox; покрытие инструментов зависит от механизма. [Permissions](https://code.claude.com/docs/en/permissions), [Sandbox](https://code.claude.com/docs/en/sandboxing).

Практическая схема для разработки: отдельные ограниченные dev credentials, отсутствие production-ключей в рабочем каталоге агента, минимальные mounts и безопасная диагностическая команда. Если агент не должен получать секрет, защищать нужно все доступные пути чтения, а не только имя `.env`.

Если он может запускать приложение с настоящим ключом и менять его код, приложение потенциально может вывести ключ. Это нужно учитывать в модели доверия. Для части API можно вынести credentials в отдельный доверенный proxy; для локальных тестов часто достаточно fake-сервисов и тестовых учёток. Один файл настроек агента не заменяет эту архитектуру.

Не нужно отдавать агенту полный dump ради ошибки подключения. Полезнее передать имя настройки, наличие, тип, источник, безопасный текст ошибки и ожидаемое поведение.

## 12. Альтернативы `.env`

Менять формат стоит ради конкретного свойства:

| Потребность | Подход | Что останется отдельной задачей |
|---|---|---|
| Вложенные структуры, типы, комментарии | TOML, JSON5, YAML | Приоритет источников и доступ |
| Проверка структуры | JSON + JSON Schema | Фактический запуск validator |
| Повторения и генерация | Jsonnet | Доставка и защита результата |
| Ограничения и объединение данных | CUE | Встраивание в приложение |
| Типизированные вычисления и imports | Dhall | Доверие к потребителю и разрешённым imports |
| Зашифрованная история конфигурации | SOPS | Доступ к ключам и plaintext после decrypt |

Источники: [TOML](https://toml.io/en/v1.1.0), [JSON5](https://spec.json5.org/), [YAML](https://yaml.org/spec/1.2.2/), [JSON Schema](https://json-schema.org/overview/what-is-jsonschema), [Jsonnet](https://jsonnet.org/), [CUE](https://cuelang.org/docs/introduction/), [Dhall](https://docs.dhall-lang.org/discussions/Safety-guarantees.html).

JSONL — отдельное JSON-значение на строку, удобное для потоков и логов; модель единого конфигурационного объекта придётся задавать отдельно. [JSON Lines](https://jsonlines.org/).

Структурированный формат не устраняет неоднозначности автоматически. JSON допускает разное поведение реализаций при повторяющихся именах; Python json оставляет последнее, TOML запрещает повторное определение ключа. [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259#section-4), [Python json](https://docs.python.org/3/library/json.html#repeated-names-within-an-object). Этот случай тоже включён в [лабораторию](experiments/format-probe.py).

Есть и способы оставить dotenv: dotenvx поддерживает encrypted values и Envfile с правилами валидации/видимости. Redaction использует точные совпадения и не скрывает все производные значения. Это готовый вариант части конфигурационного контракта, который стоит оценить прежде, чем писать свой. [dotenvx](https://github.com/dotenvx/dotenvx#readme).

## 13. Рабочий пример и справочник проблем

[Пример в репозитории](example/README.md) использует Symfony Dotenv 7.4.18 и небольшой PHP CLI. Это компонент Dotenv без полного фреймворка: так порядок загрузки виден непосредственно в bootstrap.

Compose получает `DEMO_DB_HOST` из корневого файла и явно передаёт его как `DB_HOST`. Приложение загружает собственные defaults. Искусственный токен доставляется файлом через Compose secret. PHP проверяет порт, строгий boolean и наличие токена; диагностический JSON не содержит его содержимого.

```bash
cd EnvironmentConfiguration/example
composer install --no-plugins --no-scripts
python3 check.py
docker compose -p env-guide-article run --rm --no-deps app
```

Контейнеру примера не нужна сеть: он проверяет конфигурацию и не подключается к БД. В выводе `DB_HOST` имеет значение `from-compose`, а происхождение — `process-at-bootstrap`; точный путь до исходного файла программа не выдумывает. Публичное значение показывается только для искусственного host демонстрации.

Локальные проверки покрывают defaults, внешний override, недопустимый порт/boolean, отсутствующий secret file и отсутствие содержимого fake-секрета в stdout/stderr. Это проверка конкретного примера, а не гарантия отсутствия утечек во всех приложениях.

| Симптом | Что проверить первым | Исправление |
|---|---|---|
| Файл есть, значения нет | Какой loader и путь реально используются | Подключить файл явно, проверить cwd/bootstrap |
| Compose не видит переменную из env_file | Нужна подстановка YAML или env контейнера? | Использовать источник нужной стадии |
| Local override не сработал | Внешнее окружение, порядок файлов, режим | Исправить выбранный источник; не чистить всё вслепую |
| После изменения значение старое | Дамп, config cache, процесс, сборка | Обновить конкретный производный артефакт/процесс |
| Пароль ломается на `$` или `?` | Dotenv parsing против URL parsing | Исправить нужный слой экранирования |
| PHP не видит то, что видно shell | Интерфейс загрузки, SAPI, передача окружения | Согласовать контракт приложения и запуска |
| В БД пароль остался прежним | Init-настройка или операция ротации? | Менять credential в самой БД и у клиентов |
| Ключ появился в браузере | Подставлялся ли он при frontend build? | Перенести секретную операцию на backend, отозвать ключ |
| Маска не скрыла DSN | Не стал ли секрет производным/кодированным? | Санитизировать структуру до логирования |
| Агент прочитал файл 0600 | От какого пользователя он работает? | Определить реальную границу доступа |

В собственном проекте я бы начинал с инвентаризации настроек, явного порядка загрузки и проверки при старте. Следующий шаг — диагностировать по метаданным и выдавать каждому потребителю только необходимое. Формат и количество файлов выбираются уже под эту схему.
