# Как навести порядок в env: файлы, кеш, секреты и feature flags

Во многих проектах `.env` начинается с пяти строчек, а через полгода там уже всё: порты докера, пароли, фича-флаги, настройки приложения и мониторинга. Потом появляется второй стенд, локальные переопределения и скрипт деплоя, который читает этот файл каким-то своим способом.

У меня на одной работе было восемь стендов, и управление env превращалось в кромешный ад.

По отдельности всё выглядит просто. Приколы начинаются, когда эти механизмы встречаются. Поменял значение — приложение использует старое. Подключил второй файл — победил первый. Спрятал пароль из Git — он появился в выводе диагностической команды.

Давайте пройдём этот путь на небольшом PHP-приложении с Docker Compose. Начнём с одного файла, разложим настройки, разберём загрузку и кеширование, уберём дублирование. Затем отдельно займёмся секретами и флагами, которые хочется переключать без перезапуска сервиса. Различия Symfony, Laravel и других загрузчиков будем разбирать там, где они меняют результат.

Все пароли ниже демонстрационные. Код для повторения есть в [репозитории примера](https://github.com/savinmikhail/blog/tree/main/EnvironmentConfiguration/example).

## 1. Начинаем с одного файла

Представим обычное приложение: PHP, Postgres, опубликованный HTTP-порт и новая функция, которую пока держим выключенной. Никакой интерполяции, просто значения:

```dotenv
APP_HTTP_PORT=8080
APP_ENV=dev
DB_HOST=db
DB_PORT=5432
DB_NAME=app
DB_USER=app
DB_PASSWORD=demo-password
DATABASE_URL=postgresql://app:demo-password@db:5432/app
FEATURE_NEW_CHECKOUT=false
```

На одном компьютере с этим можно жить. Потом одному разработчику нужен порт 8081, в тестах БД называется иначе, а на стенде другой пароль. Кто-то меняет tracked-файл, кто-то хранит свою копию, а в README появляется просьба «не забудьте поправить эти семь строчек».

Прежде чем раскладывать настройки, надо разобраться с одной вещью: **файл `.env` и окружение процесса — разные вещи**. Сам файл ничего не передаёт приложению. Его читает конкретный инструмент: библиотека dotenv, Symfony, Compose или shell. У каждого свой результат и свои правила.

Например, PHP-загрузчик может заполнить `$_ENV`, но это не обязательно то же самое, что `getenv()`. Способ запуска PHP и настройки SAPI тоже влияют на доступные значения. Поэтому в приложении я бы выбрал один интерфейс конфигурации и передавал проверенные значения сервисам, вместо чтения env вперемешку по всему коду. [PHP getenv](https://www.php.net/manual/en/function.getenv.php), [phpdotenv](https://github.com/phpdotenv/phpdotenv).

Окружение дочерний процесс получает при запуске. Если поменять переменную в другом терминале, уже работающий воркер от этого не обновится. К этому ещё вернёмся, когда дойдём до кеша и флагов.

Первую проблему — разные настройки на разных машинах — решим без копирования всего файла.

## 2. Разделяем общие настройки и локальные переопределения

Общие значения оставим в `.env`, отличия конкретной машины перенесём в `.env.local`:

```dotenv
# .env.local
APP_HTTP_PORT=8081
DB_PASSWORD=another-demo-password
DATABASE_URL=postgresql://app:another-demo-password@db:5432/app
```

Пока пароль и DSN приходится менять вместе. Это заметное дублирование, но сначала наведём порядок в источниках. Интерполяцию добавим, когда станет понятно, кто именно загружает файлы.

`.env.local` исключаем из Git. В базовом файле оставляем несекретные defaults и явно демонстрационные значения для изолированной разработки. Настоящий пароль production в репозитории не нужен. А запуск production с `change-me` должен заканчиваться ошибкой, до подключения к внешним системам.

Ещё одно разделение — инфраструктура и приложение:

```text
.env                  # порты Compose и другие настройки запуска сервисов
.env.local            # их локальные переопределения
app/.env              # общие настройки PHP-приложения
app/.env.local        # локальные настройки приложения
```

В корне нашего примера останется `APP_HTTP_PORT`. Адрес БД, её имя, пароль и флаг переедут в `app/`. PHP не нужен внешний порт, на котором nginx принимает запросы; nginx не нужен пароль БД.

Но разделить файлы — полдела. Само по себе такое дерево не создаёт наследование между корнем и `app/`. Если значение нужно двум потребителям, его надо явно передать обоим. Как — покажу в разделе про Compose.

### Что коммитить

Соглашения фреймворков отличаются. Symfony предполагает общие `.env` и environment-specific файлы в Git, local overrides вне Git. Laravel предлагает исключать рабочий `.env` и поддерживать `.env.example`. [Symfony](https://symfony.com/doc/current/configuration.html#overriding-environment-values-via-env-local), [Laravel](https://laravel.com/docs/12.x/configuration#environment-configuration).

Для Symfony-проекта я бы оставил несекретные defaults в штатной иерархии. В Laravel использовал бы его соглашение, а актуальность `.env.example` проверял вместе с обязательными настройками приложения. Это избавляет от собственного протокола загрузки поверх фреймворка.

В большом файле помогают группы комментариев: БД, почта, мониторинг, внешние API. По `.env.example` должно быть понятно, что нужно для старта, что опционально и куда получить недостающий секрет. Копировать его из production со значениями — плохой способ поддерживать документацию.

Файлы появились. Теперь нужно однозначно договориться, в каком порядке они читаются.

## 3. Загружаем файлы и разбираемся с приоритетами

Для PHP-примера возьмём Symfony Dotenv. Минимальная загрузка выглядит так:

```php
use Symfony\Component\Dotenv\Dotenv;

(new Dotenv())->loadEnv(__DIR__.'/.env');
```

Здесь `__DIR__` — каталог приложения. `loadEnv()` использует соглашения Symfony: базовый файл, local override, затем файлы выбранного окружения.

```text
.env
.env.local
.env.<environment>
.env.<environment>.local
```

В стандартной загрузке более поздние слои переопределяют ранние, настоящие внешние значения сохраняются. Для `test` общий `.env.local` пропускается, чтобы личные настройки не меняли тестовое окружение. Явная настройка `overrideExistingVars` позволяет изменить поведение внешних значений. [Symfony configuration](https://symfony.com/doc/current/configuration.html#overriding-environment-values-via-env-local).

Допустим, в `app/.env` записано `DB_HOST=db`, в local — `DB_HOST=local-db`. Но приложение запускают так:

```bash
DB_HOST=from-process php app/config.php
```

Внешнее значение выиграет. Поэтому при «local не подхватился» первым делом стоит посмотреть, не задана ли переменная раньше — в терминале, IDE, process manager или контейнере.

С другими загрузчиками порядок нужно уточнять отдельно:

| Загрузчик | Что важно для переопределения |
|---|---|
| Laravel | Внешние значения выше файла; выбор `.env.<environment>` и config cache имеют свои правила |
| Node `--env-file` | Внешнее окружение выше файлов; поздний файл перекрывает ранний |
| python-dotenv | Существующие env сохраняются по умолчанию; `override=True` меняет поведение |

Источники: [Laravel](https://laravel.com/docs/12.x/configuration#environment-configuration), [Node CLI](https://nodejs.org/api/cli.html#--env-filefile), [python-dotenv](https://bbc2.github.io/python-dotenv/).

Пустая строка тоже может быть переопределением. `KEY=` и отсутствие `KEY` полезно проверять разными сценариями: иначе «очистить настройку» неожиданно превращается в «вернуть default».

С загрузкой внутри PHP разобрались. Теперь посмотрим, что до этого делает Docker Compose.

## 4. Передаём настройки через Docker Compose

В корневом `.env` у нас лежит порт:

```dotenv
APP_HTTP_PORT=8080
```

Compose использует его при построении конфигурации:

```yaml
services:
  app:
    image: example/app
    ports:
      - "${APP_HTTP_PORT}:80"
```

Compose подставил порт в YAML. В окружении PHP переменная от этого не появилась. В данном случае она там и не нужна.

Для подстановок Compose берёт значения из shell и env-файлов. Несколько файлов можно передать явно:

```bash
docker compose --env-file .env --env-file .env.local config
```

Здесь оба файла должны существовать. Поздний файл перекрывает ранний, а значение из shell может перекрыть оба. Пути к `--env-file` отсчитываются от рабочей директории команды. [Compose interpolation](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/).

Если не хочется повторять аргументы, можно использовать экспортированную переменную:

```bash
export COMPOSE_ENV_FILES=.env,.env.local
docker compose config
```

### Как значение попадает в контейнер

Допустим, адрес БД должен задать сам запуск сервиса, а приложение продолжит читать остальные defaults из `app/.env`. Передаём его явно:

```yaml
services:
  app:
    image: example/app
    environment:
      DB_HOST: db
```

Symfony увидит внешнее `DB_HOST`, и оно выиграет у файла. Другой вариант — передать файл целиком через service `env_file`:

```yaml
services:
  app:
    image: example/app
    env_file:
      - path: ./app/.env
        required: true
      - path: ./app/.env.local
        required: false
```

`required: false` поддерживается с Compose 2.24. Service `env_file` задаёт окружение контейнера; он не даёт значения для `${...}` в остальных местах YAML. Это и есть две стадии, которые легко перепутать. [Services reference](https://docs.docker.com/reference/compose-file/services/#env_file).

В окружении контейнера `environment` выше `env_file`, даже для явно пустого значения; `env_file` выше `ENV` образа. Для `docker compose run` есть ещё CLI-переопределение `-e`. А после запуска PHP применит собственные правила загрузки файлов. [Container env precedence](https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/).

Для нашего PHP-примера выберем чтение app-файлов самим приложением, а через Compose передадим только нужные внешние значения. Так настройки приложения не надо автоматически экспортировать всем процессам контейнера. У контейнера Postgres будет другой набор — тот, который понимает его entrypoint.

Если одновременно передать один файл через `env_file` и смонтировать для PHP, появятся два пути доставки. Окружение сохранится при создании контейнера, а файл живёт отдельно. После обновления файла старое process env может продолжить побеждать. Поэтому для каждой настройки полезно выбрать один основной путь.

### Сборка и запуск — разные моменты

Dockerfile `ARG` относится к сборке; `ENV` задаёт значения окружения в образе. Настройка, использованная при сборке, не обязана реагировать на env при запуске. Во frontend это особенно видно: собранный JS уже содержит подставленные строки.

Для скачивания приватных зависимостей во время build используйте build secrets. Credentials в `ARG`, `ENV` или скопированном файле могут оставить след в образе или его метаданных. [Docker build secrets](https://docs.docker.com/build/building/secrets/).

### Одна сборка фронтенда для разных стендов

На работе мы выносили настройки фронтенда, отличающиеся между стендами, в JSON, который отдавал nginx бэкенда. Перед запуском приложения фронт загружал этот файл: его значения перекрывали настройки сборки, а итоговая конфигурация проверялась схемой. В коде адрес файла задавался через `VITE_ENV_FILE`.

Так можно продвигать одну сборку фронта между стендами, меняя адреса API и другие публичные параметры отдельно от JS. Обычные `import.meta.env` Vite подставляет при сборке; чтобы получать значения при открытии страницы, мы явно добавили загрузчик JSON. [Vite env](https://vite.dev/guide/env-and-mode).

Отдавать файл именно с бэкенда необязательно: отдельный `config.json` можно положить рядом со статикой и подменять при деплое. Для одной сборки адрес загрузки должен подходить всем стендам — например, быть относительным. Важно дождаться конфигурации до первых запросов приложения и настроить её кеширование отдельно от JS-бандлов. Всё, что получил браузер, доступно пользователю, поэтому отдаём только явно выбранные публичные настройки. Уже открытая вкладка сама новый конфиг не подхватит — для этого нужен reload или отдельный механизм обновления.

Теперь наша схема умеет выбирать и передавать настройки. Можно оптимизировать её загрузку — но это добавит ещё одно место, где сохраняется значение.

## 5. Кешируем конфигурацию и понимаем, что обновлять

В полноценном Symfony-проекте с Flex dotenv-файлы можно заранее собрать в `.env.local.php`:

```bash
composer dump-env prod
```

После этого стандартный bootstrap использует готовый дамп вместо повторного парсинга текстовых файлов. Поэтому изменение `.env.local` при наличии действующего дампа ещё не меняет загружаемые defaults: дамп надо пересоздать. Внешние env и настройки bootstrap продолжают участвовать в выборе значения. [Symfony dotenv production](https://symfony.com/doc/current/configuration.html#configuring-environment-variables-in-production).

В минимальном bootstrap из третьего раздела мы вызываем `loadEnv()` — он этот PHP-дамп не читает. У компонента для этого есть `bootEnv()`, а стандартный Symfony bootstrap уже учитывает такую загрузку. Финальная CLI-лаборатория оставлена на текстовых файлах; команду Flex и кеш фреймворка надо проверять в самом Symfony-проекте.

Это отдельная оптимизация от кеша DI-контейнера. Обычные `%env(...)%` и значения, разрешённые при компиляции контейнера, имеют разный момент чтения. `cache:clear` не стоит превращать в универсальное лечение любой проблемы с env. [Env processors](https://symfony.com/doc/current/configuration/env_var_processors.html#resolving-environment-variable-at-compile-time), [Deployment](https://symfony.com/doc/current/deployment.html).

В Laravel похожая по цели, но другая по поведению команда:

```bash
php artisan config:cache
```

Она сохраняет вычисленную конфигурацию. После этого Laravel не загружает `.env` для запросов и Artisan, а `env()` видит только внешние переменные. Отсюда правило: `env()` вызываем в config-файлах, в приложении читаем `config()`. После изменения источников config cache пересобираем; для удаления есть `config:clear`. [Laravel configuration caching](https://laravel.com/docs/12.x/configuration#configuration-caching).

### А если значение всё равно старое

Может жить старый процесс. Например, queue worker загрузил настройки при старте и продолжает с ними работать. У Laravel для завершения воркеров после текущей задачи есть `queue:restart`; process manager должен запустить их заново. [Queue deployment](https://laravel.com/framework/docs/12.x/queues#queue-workers-and-deployment).

Удобно разделять действия так:

| Что изменили | Что обновляем |
|---|---|
| Symfony dotenv при наличии дампа | `.env.local.php` |
| Laravel config/env при активном config cache | Config cache |
| Окружение контейнера в Compose | Затронутый контейнер пересоздаём; простой restart не применяет новый env |
| Настройки долгоживущего процесса | Его reload/restart по предусмотренному механизму |
| Frontend build-time значение | Пересобираем и доставляем bundle |

Про Compose restart это прямо [сказано в документации](https://docs.docker.com/reference/cli/docker/compose/restart/).

Ещё один неприятный случай — состояние БД. В официальном Postgres-образе `POSTGRES_PASSWORD` применяется при первоначальной инициализации пустого каталога данных. Изменение env не меняет пароль уже существующей роли. Нужна ротация в самой БД и обновление клиентов. Удалять volume ради нового пароля нельзя: вместе с ним исчезнут данные. [Postgres image](https://github.com/docker-library/docs/tree/master/postgres#environment-variables).

Мы разобрались, когда настройки загружаются и сохраняются. Вернёмся к оставленной проблеме: пароль в наших файлах до сих пор повторяется внутри `DATABASE_URL`.

## 6. Убираем дублирование и разбираемся с интерполяцией

Вместо двух независимых копий одного значения хочется написать так:

```dotenv
DB_HOST=db
DB_PORT=5432
DB_NAME=app
DB_USER=app
DB_PASSWORD=demo-password
DATABASE_URL="postgresql://${DB_USER}:${DB_PASSWORD}@${DB_HOST}:${DB_PORT}/${DB_NAME}"
```

Загрузчик раскрывает ссылки на другие переменные — это и есть интерполяция. Теперь прежде, чем менять пароль, нужно понять, **на каком этапе собирается DSN**.

Допустим, local-файл переопределяет `DB_HOST=local-db`. Изменится ли host внутри `DATABASE_URL`? В проверенном Symfony Dotenv 7.4.18 `loadEnv()` пересчитал зависимую строку после загрузки слоёв. В [примере](https://github.com/savinmikhail/blog/blob/main/EnvironmentConfiguration/example/dotenv-probe.php) итоговый host и URL используют local-значение.

Но если отдельно прочитать два файла через Python `dotenv_values()`, строки интерполируются при чтении каждого файла. Последующее объединение словарей само по себе не пересобирает URL. [python-dotenv](https://bbc2.github.io/python-dotenv/).

Поэтому я бы назначил одно место сборки DSN: либо загрузчик с проверенными правилами, либо код приложения после получения всех компонентов. Если строку уже собрал Compose, дополнительный expand в приложении нужно учитывать отдельно: `compose config` тогда показывает промежуточный результат.

### Один файл, разные парсеры

Файл dotenv похож на shell, но единой грамматики для всех инструментов нет. Node, например, публикует собственные правила. [Node env specification](https://nodejs.org/api/environment_variables.html).

На таком искусственном файле:

```dotenv
BASE=alpha
EXPANDED=${BASE}/data
LITERAL=cost$$cash
```

получились разные результаты:

| Обработчик | EXPANDED | LITERAL |
|---|---|---|
| Node `--env-file` | `${BASE}/data` | `cost$$cash` |
| Bash `source` | `alpha/data` | `cost<PID>cash` |
| Make `include` с export | `alpha/data` | `cost$cash` |
| Compose `config --format json` | `alpha/data` | `cost$$cash` |

У Compose здесь показан вывод модели, который может экранировать `$`, а не буквальное значение в контейнере. [Скрипты и версии опыта](https://github.com/savinmikhail/blog/tree/main/EnvironmentConfiguration/experiments). Bash и Make включены потому, что ими часто подгружают те же файлы; их собственная грамматика никуда от этого не исчезает.

Для обычного `.env` Compose:

| Запись | Значение |
|---|---|
| `VALUE="${BASE}/data"` при BASE=alpha | `alpha/data` |
| `VALUE='${BASE}/data'` | Буквальная `${BASE}/data` |
| `VALUE=hello # comment` | `hello` |
| `VALUE=hello#world` | `hello#world` |
| `VALUE="hello # world"` | `hello # world` |
| `VALUE=` | Пустая строка |

Двойные кавычки поддерживают escape-последовательности вроде `\n`, одинарные оставляют их буквальными. Одинарно заключённое значение может занимать несколько строк. Для service `env_file` есть `format: raw` с Compose 2.30: он передаёт значения, включая кавычки и `$`, без обычной интерполяции. [Compose syntax](https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/#env-file-syntax), [env_file raw](https://docs.docker.com/reference/compose-file/services/#env_file).

### Кавычки не заменяют URL encoding

Наш простой `demo-password` удобно подставляется в DSN. А если в пароле есть `@`, `?` или `#`? Сначала строку разбирает dotenv, потом URL-парсер клиента БД. Кавычки решают первую задачу, но не вторую.

В PHP можно кодировать отдельные компоненты:

```php
$user = rawurlencode($dbUser);
$password = rawurlencode($dbPassword);
$dsn = "postgresql://{$user}:{$password}@{$dbHost}:{$dbPort}/{$dbName}";
```

Host, port и имя БД здесь уже проверены. Кодировать целиком готовый URL нельзя, повторно кодировать уже обработанный пароль тоже не надо. Синтаксис самого DSN выбирается под драйвер. [PHP rawurlencode](https://www.php.net/manual/en/function.rawurlencode.php).

Чтобы не держать в голове кавычки dotenv и URL одновременно, в конечном примере DSN собирается в PHP из проверенных компонентов. Следующий шаг — сделать эти проверки явными.

## 7. Проверяем значения и генерируем секреты

Файл может успешно распарситься и всё равно содержать нерабочую конфигурацию. Например, порт `70000`, пустой host или опечатку `flase` в boolean.

В PHP `(bool) 'false'` даёт true. Для нашего флага примем только строки `true` и `false`; всё остальное считаем ошибкой. Для порта — целое число от 1 до 65535. Для обязательного секрета — непустое значение. Это правила приложения, которые должны выполниться до запуска его основной работы.

Symfony предлагает processors `int:`, `bool:`, `json:`, `file:` и другие. Они помогают получать нужный тип, но диапазоны, обязательность и зависимости интеграций надо определить отдельно. `resolve:` раскрывает `%parameter%` Symfony, а `${VARIABLE}` dotenv относится к другой стадии. [Env processors](https://symfony.com/doc/current/configuration/env_var_processors.html).

Production guard дополняет такие проверки: он отклоняет известные dev-значения и placeholders. Но проверка «не равно change-me» пропустит `admin123`. Собственные токены стоит генерировать криптографически, например через `bin2hex(random_bytes(32))`, и сохранять прямо в защищённый файл или хранилище. [PHP random_bytes](https://www.php.net/manual/en/function.random-bytes.php).

Команда генерации должна быть повторяемой в смысле процедуры, а не результата: новый секрет при каждом деплое без согласованной ротации только сломает клиентов. Уже работающие значения не стоит молча перезаписывать.

### Генератор тоже читает dotenv

Когда появляется второй стенд, хочется автоматизировать подготовку его конфигурации: создать недостающие секреты, сохранив уже выданные. Так в цепочке появляется собственный скрипт «дописать недостающие секреты». В одном таком скрипте на искусственном файле простое разделение по `=` приняло комментарий за настройку, сохранило кавычки вокруг placeholder и посчитало `export MODE` именем ключа. Генератор и runtime-загрузчик должны одинаково понимать файл.

Для записи нужны разрешённые ключи, закрытый временный файл и атомарная подмена. Резервная копия содержит те же секреты и требует таких же прав и срока хранения. Проверка symlink перед записью сама по себе не закрывает гонку между проверкой и использованием пути.

### Какие проверки стоит автоматизировать

| Проверка | Что ловит |
|---|---|
| Linter dotenv | Выбранные правила синтаксиса и оформления |
| Compose config | Ошибки модели и подстановок; его вывод может содержать секреты |
| Проверка при старте | Неверные типы, диапазоны и зависимости настроек |
| Production guard | Отсутствующие секреты и запрещённые defaults |
| Secret scanner | Известные признаки credentials в файлах и истории |

Если в проекте регулярно ломают формат файлов, можно добавить [dotenv-linter](https://github.com/dotenv-linter/dotenv-linter). Это отдельная опциональная проверка, а не обязательная ступень ради самой ступени. [Gitleaks](https://github.com/gitleaks/gitleaks) решает другую задачу — ищет признаки секретов; его полезно запускать до коммита и в CI по выбранной политике дерева/истории.

Итак, значения приходят из понятных источников и проверяются. Но пароль всё ещё живёт в обычном env. Посмотрим, как уменьшить его распространение.

## 8. Выдаём секрет только нужному потребителю

Сначала разделим параметры и секреты. Порт приложения не равен паролю БД. При этом в конкретной системе даже hostname или идентификатор клиента может быть чувствительным — выводить настройки целиком я бы не стал.

Для нашего примера уберём `DB_PASSWORD` и готовый `DATABASE_URL` из dotenv. Пароль положим в отдельный файл и передадим PHP его путь:

```yaml
services:
  app:
    image: example/app
    environment:
      DB_PASSWORD_FILE: /run/secrets/db_password
    secrets:
      - db_password
secrets:
  db_password:
    file: ./secrets/db-password.txt
```

Приложение читает файл и собирает DSN в памяти. Содержимое пароля больше не нужно передавать как обычную переменную окружения всем дочерним процессам. Суффикс `_FILE` работает потому, что его поддерживает наш код; произвольный образ от имени переменной читать файл не научится. [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).

Так мы сократили один путь распространения секрета. Приложение по-прежнему может прочитать пароль, поэтому ошибка или изменённый код способны его вывести. У пользователя с доступом к файлу на хосте он тоже остаётся доступен. File-based Compose secrets используют bind mount, не шифруют исходник; `uid/gid/mode` для источника `file` не изменяют его права через YAML. [Services reference](https://docs.docker.com/reference/compose-file/services/#secrets).

### Где хранить и как доставлять

Если конфигурацию нужно версионировать зашифрованной, есть [SOPS](https://github.com/getsops/sops). Если нужны управляемая выдача, отзыв, аудит и короткоживущие credentials — стоит смотреть на secret manager с подходящими возможностями. Ключ дешифровки и доступ к manager тоже требуют отдельного решения.

В Kubernetes это разделение выражено через ConfigMap для обычной конфигурации и Secret для конфиденциальных данных. Secret не означает автоматического шифрования в etcd: нужны настройки encryption at rest и права. Env в уже запущенном Pod не обновится от правки объекта; файловая доставка обновляется по другим правилам, а приложение должно перечитать файл. Mount через `subPath` таких обновлений не получает. [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/), [ConfigMaps](https://kubernetes.io/docs/concepts/configuration/configmap/).

Если секрет ротируется заменой файла, проверьте обе стадии: увидел ли новый файл mount и перечитал ли его процесс. При атомарной замене single-file bind mount может продолжить ссылаться на старый файл; одного успешного `rename` на хосте недостаточно.

Для небольшого Compose-проекта я бы начинал с явной выдачи нужных значений каждому сервису и файлов для подходящих секретов. Это можно сделать без обязательного переезда всей инфраструктуры в Kubernetes или Vault.

В CI приватный файл можно доставлять через file variables, не сохраняя его содержимое в общем артефакте. Продумайте владельца, права, временные копии и передачу до конечного потребителя; отключите вывод значения через shell tracing. File variable даёт путь к файлу, а не запрет скрипту его читать. [GitLab variables](https://docs.gitlab.com/ci/variables/).

Теперь пароль хранится отдельно. Осталось не превратить само чтение конфигурации в исполнение чужих команд.

## 9. Загружаем данные, не исполняя файл вслепую

Очень хочется написать `source .env`, чтобы настройки появились в shell. Но shell прочитает файл как программу:

```dotenv
VALUE=$(printf synthetic-command-ran)
```

Bash выполнит `printf`. Встроенный Node `--env-file` в [том же опыте](https://github.com/savinmikhail/blog/blob/main/EnvironmentConfiguration/experiments/format-probe.py) оставил выражение строкой.

Если атакующий может изменить файл, который затем загрузит доверенный deploy/CI-скрипт через `source`, команды выполнятся с правами этого скрипта. Расширение `.env` shell не ограничивает.

`Make include` тоже использует свой язык, PHP/JS-конфиги являются кодом. И даже специализированная библиотека может поддерживать команды: Symfony Dotenv 7.4.18 раскрывает `$()` на Unix при наличии Symfony Process; без него выдаёт ошибку. Dotenvx также поддерживает command substitution. [Symfony source](https://github.com/symfony/dotenv/blob/v7.4.18/Dotenv.php), [dotenvx](https://github.com/dotenvx/dotenvx#readme).

Поэтому безопасный helper в конце пайплайна не решает проблему, если перед ним Make уже сделал `include .env.local`. Я встретил такое сочетание при разборе своих проектов. Проверять надо реальную команду запуска целиком: какой язык на каждом шаге читает файл и что именно подтверждает preflight.

Значение может управлять и самим рантаймом. Например, Node применяет `NODE_OPTIONS` из `--env-file`, включая разрешённые preload-настройки. У `dotenv.config()` внутри уже запущенного процесса другой момент применения — это не то же самое. [Node CLI](https://nodejs.org/api/cli.html#--env-filefile).

### Уязвимости бывают и в библиотеке

У npm JSON5 была prototype pollution возвращаемого объекта, исправленная в 1.0.2/2.2.2. У python-dotenv — перезапись файла через symlink при cross-device fallback в `set_key`/`unset_key`, с указанным исправлением 1.2.2. Первый случай относится к парсингу объекта, второй — к записи файла; обычное чтение `.env` не превращается от них в универсальное RCE. [JSON5 advisory](https://github.com/json5/json5/security/advisories/GHSA-9c47-m6qq-7p4h), [python-dotenv advisory](https://github.com/theskumar/python-dotenv/security/advisories/GHSA-mf9w-mj56-hr94).

При выборе библиотеки я бы проверял её возможности по операциям: что она делает при чтении, какие вычисления разрешает и как записывает изменения. Advisory имеет смысл сопоставлять с используемой версией и конкретным вызовом.

С механизмом загрузки определились. А вот флаг checkout всё ещё лежит рядом со startup-настройками. Удобно ли это для управления функцией?

## 10. Переносим оперативные флаги из env

Допустим, новый checkout уже выкатили, но включать его всем пока не хотим. Env-флаг подходит, чтобы выбрать поведение при старте. А если надо открыть функцию десяти процентам пользователей или быстро выключить после ошибки?

```dotenv
FEATURE_NEW_CHECKOUT=false
```

Менять env у каждой реплики ради такого действия неудобно. В обычном startup-сценарии понадобится обновить конфигурацию процесса или пересоздать контейнер. Новая сборка образа для этого не обязательна, но мгновенного переключателя из env не получается.

Для оперативного управления флагами можно использовать таблицу БД с управлением или специализированный сервис. В env останутся адрес этого источника, credentials и настройки клиента. Решение о функции приложение будет получать через отдельный интерфейс feature flags.

В коде меняется источник решения. Схематически, через свой интерфейс флагов:

```php
// Раньше: снимок startup-конфигурации
if ($config->featureNewCheckout) { /* ... */ }

// Теперь: решение из выбранного источника для этого контекста
if ($flags->isEnabled('new-checkout', $userContext)) { /* ... */ }
```

Важно, что сама таблица динамику не создаёт. Если при старте прочитать её в readonly-объект, получится тот же снимок. Нужен выбранный механизм обновления: чтение при обращении, TTL, polling или события. Разные реплики могут заметить изменение в разное время; для одной операции стоит определить, когда фиксируется решение.

Например, [Unleash PHP SDK](https://docs.getunleash.io/sdks/php#caching) использует TTL-кеш и stale-cache при ошибках получения конфигурации. Нажали кнопку в панели — приложение увидит новое значение после предусмотренного refresh. [OpenFeature](https://openfeature.dev/docs/reference/concepts/provider/) даёт API вычисления флага и provider-интерфейс для выбранного источника; это не само хранилище. [Evaluation API](https://openfeature.dev/specification/sections/flag-evaluation/) предусматривает default и контекст вычисления.

Для флага заранее выбираем поведение при сбое, допустимую задержку, права изменения и аудит. Безопасный fallback зависит от функции, не всегда это `false`. Флаг не заменяет проверку прав и не должен хранить секрет. Закончили временный rollout — убираем развилку из кода; постоянные operational toggles живут по другой политике. [Unleash lifecycle](https://docs.getunleash.io/concepts/feature-flags#feature-flag-lifecycle).

В лабораторном PHP-примере флаг остаётся стартовым boolean: он показывает границу, после которой нужен другой источник. Установка полноценного flag-сервиса — уже самостоятельный выбор проекта.

Наш пример прошёл путь от одного файла до нескольких механизмов. Теперь нужна отладка, которая поможет разобраться в них и не опубликует пароль заодно.

## 11. Отлаживаем конфигурацию, не раскрывая её целиком

Первый соблазн — вывести `env`, `$_ENV`, `phpinfo` или весь `docker compose config`. В [опыте с Compose](https://github.com/savinmikhail/blog/blob/main/EnvironmentConfiguration/experiments/leak-probe.py) API key из `environment` оказался в выводе открытым текстом. Поэтому я бы начинал с вопроса к конкретной настройке: она есть, валидна и откуда пришла?

```text
DB_PORT           present=yes  valid=yes  origin=dotenv
DB_PASSWORD_FILE  present=yes  valid=yes  content_present=yes
```

Из готовой строки нельзя восстановить всю историю загрузки. Наш пример запоминает, какие ключи были доступны до bootstrap, и различает `process-at-bootstrap` и `dotenv`. Для точного имени файла и цепочки overrides нужна поддержка загрузчика или отдельная проверенная диагностика.

Можно проверять и отношения между настройками: совпадают ли ключи подписывающего и проверяющего сервисов. Результата `matches`/`MISMATCH` часто достаточно; показывать значения и их хеши не требуется. Но сравнивать надо те источники, которые действительно использует приложение, а не произвольную копию файла.

### Куда ещё уезжает секрет

Пароль способен попасть в сообщение ошибки, profiler, конфигурационный кеш, build context, CI-артефакт или аргументы дочернего процесса. Validator может не печатать значение, но передавать его в `argv`; доступность аргументов наблюдателю зависит от ОС и настроек. Контролируемый stdin убирает этот канал, но не изолирует от привилегированного читателя.

`APP_DEBUG=true` в production может раскрыть конфигурацию через страницу ошибки. Приватные dotenv и сгенерированные дампы надо защищать как исходные секреты. А для `COPY . .` отдельно нужен `.dockerignore`: `.gitignore` не управляет build context. [Laravel debug](https://laravel.com/docs/12.x/configuration#debug-mode), [Docker context](https://docs.docker.com/build/concepts/context/#dockerignore-files).

Во frontend значение, включённое в JS, доступно пользователю браузера независимо от Git. Поэтому Vite предупреждает не класть secrets в `VITE_*`. [Vite env](https://vite.dev/guide/env-and-mode).

Маскирование полезно для вывода. Например, Spring Actuator скрывает значения диагностических endpoints по умолчанию. Но маска не запрещает процессу читать данные, а точное совпадение пароля не гарантирует удаления его URL-encoded копии из DSN. [Spring sanitization](https://docs.spring.io/spring-boot/reference/actuator/endpoints.html#actuator.endpoints.sanitization), [GitLab masking](https://docs.gitlab.com/ci/variables/).

### А если диагностику выполняет LLM-агент

Агент может открыть файл, запустить `printenv`, прочитать дамп или написать небольшой скрипт. Запрет одному Read-инструменту не закрывает остальные пути. `.gitignore` вообще про Git, а файл 0600 доступен агенту, если тот работает от его владельца. Механизмы permissions и OS sandbox имеют разное покрытие инструментов. [Claude permissions](https://code.claude.com/docs/en/permissions), [Sandbox](https://code.claude.com/docs/en/sandboxing).

Для разработки я бы дал агенту отдельные ограниченные dev credentials и команду безопасной диагностики. Production-ключам незачем лежать в его рабочем каталоге. Если же агент может менять код приложения и запускать его с настоящим ключом, код способен вывести этот ключ — это уже граница доверия к исполнению. Для части API можно использовать отдельный доверенный proxy, для тестов — fake-сервис.

Вместо полного дампа агенту можно передать имя настройки, наличие, тип, известный источник и текст ошибки без DSN. Ему будет достаточно контекста для многих ошибок загрузки.

Если секрет уже раскрылся, удаление строки из Git не отзывает его. Нужны отзыв/ротация, проверка использования и устранение канала утечки. Публичные `.env` действительно использовали для получения облачных credentials. [Unit 42](https://unit42.paloaltonetworks.com/large-scale-cloud-extortion-operation/).

У нас уже есть понятные правила работы с env. Остаётся вопрос: может, надо было сразу выбрать другой формат?

## 12. Когда стоит выбрать другой формат

Если проблема в том, что приложение не перечитывает настройку, переход с dotenv на JSON этого не исправит. Формат помогает с другой частью задачи: структура, типы, комментарии и проверка данных.

Для простой плоской конфигурации dotenv вполне хватает. Когда появляются вложенные разделы и массивы, удобнее смотреть на [TOML](https://toml.io/en/v1.1.0), [JSON5](https://spec.json5.org/) или [YAML](https://yaml.org/spec/1.2.2/). Структуру и ограничения можно проверять схемой, например [JSON Schema](https://json-schema.org/overview/what-is-jsonschema) после совместимого разбора данных.

Когда конфигурация десятков сервисов повторяется, полезны средства генерации и композиции: [Jsonnet](https://jsonnet.org/), [CUE](https://cuelang.org/docs/introduction/), [Dhall](https://docs.dhall-lang.org/discussions/Safety-guarantees.html). Они добавляют собственные правила и инструменты, поэтому ради десятка строк я бы такую систему не затаскивал.

Даже у структурированного формата надо определить неоднозначности. Python JSON parser по умолчанию оставляет последнее повторяющееся имя, TOML запрещает повторное определение ключа. Это есть в [небольшом опыте](https://github.com/savinmikhail/blog/blob/main/EnvironmentConfiguration/experiments/format-probe.py). [RFC 8259](https://www.rfc-editor.org/rfc/rfc8259#section-4), [Python json](https://docs.python.org/3/library/json.html#repeated-names-within-an-object).

[JSONL](https://jsonlines.org/) удобен для независимых записей и потоков; для единого конфига правила объединения придётся придумывать отдельно. А [dotenvx](https://github.com/dotenvx/dotenvx#readme) позволяет сохранить dotenv и добавить encrypted values, контракт Envfile и redaction. Производные значения требуют отдельного внимания и там.

Выбирать стоит под проблему: структура — к формату и схеме, повторения — к композиции, секреты — к выдаче и правам, оперативные флаги — к динамическому источнику.

## 13. Собираем пример и проверяем, что получилось

В [примере](https://github.com/savinmikhail/blog/tree/main/EnvironmentConfiguration/example) итоговая схема устроена так:

```text
.env                         # внешнее переопределение host для Compose
app/.env                     # defaults приложения, без пароля
app/.env.local               # личные overrides, если нужны
app/config-values.php        # загрузка, проверка, сборка DSN
app/config.php               # безопасный отчёт
secrets/db-password.txt       # демонстрационный пароль для лаборатории
compose.yaml                 # явная передача внешнего host и secret-file
```

Compose использует корневой файл, PHP читает свои app-файлы, пароль приходит отдельным файлом. DSN собирается в PHP, стартовый флаг разбирается строго. В диагностическом выводе нет пароля и DSN.

```bash
cd EnvironmentConfiguration/example
composer install --no-plugins --no-scripts
python3 check.py
php dotenv-probe.php
docker compose -p env-guide-article run --rm --no-deps app
```

В начале мы использовали условный HTTP-порт, чтобы показать подстановку в YAML. Итоговая лаборатория — небольшой CLI с Symfony Dotenv, без HTTP-сервера и подключения к БД: его удобно запускать ради самой конфигурации. Контейнер работает без сети. Версии и результаты проверок — в README рядом с кодом.

Для отладки настоящего проекта я бы шёл в таком порядке:

| Симптом | С чего начать |
|---|---|
| Изменение вообще не влияет | Проверить checkout, Compose project, image и фактический mount |
| Файл есть, переменной нет | Уточнить loader, путь и рабочую директорию |
| Local override не сработал | Проверить внешнее env и порядок файлов |
| Compose не видит значение из env_file | Развести подстановку YAML и окружение сервиса |
| Значение осталось старым | Найти конкретный дамп, config cache или долгоживущий процесс |
| Пароль ломается на спецсимволах | Отдельно проверить dotenv parsing и URL encoding |
| Postgres не принял новый пароль | Проверить ротацию существующей роли, а не init-переменную |
| Флаг в панели изменён, поведение прежнее | Проверить TTL, fallback, реплику и момент чтения |
| Ключ появился в браузере или логе | Отозвать его, затем найти путь раскрытия |

Начать можно с малого: разнести настройки, явно выбрать порядок загрузки и проверять итоговые значения при старте. Дальше у каждого усложнения будет понятная причина: кеш экономит повторную загрузку, интерполяция убирает дублирование, отдельная выдача сокращает распространение секретов, а хранилище флагов позволяет управлять функциями независимо от запуска процесса.

А какие сюрпризы с env попадались вам? Особенно интересно, где проверка и реальный запуск неожиданно читали разные значения.
