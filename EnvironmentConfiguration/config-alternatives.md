# Альтернативы dotenv: формат, контракт, вычисление и доставка

Проверено 16 октября 2026 по первичной документации. Это дополнение к исследованию, не рекомендация переписать текущие проекты. Проверенные уязвимости отдельно в `config-vulnerabilities.md`.

## Четыре независимых выбора

1. **Формат данных**: dotenv, JSON/JSON5, TOML, YAML, INI. Определяет структуру и правила парсинга.
2. **Контракт и разрешение источников**: типы, обязательность, defaults, overrides, неизвестные ключи, кеш/reload. Само расширение файла этого не задаёт.
3. **Вычисление**: интерполяция, функции, imports, shell-команды. Чем больше возможностей, тем важнее граница доверия.
4. **Доставка секрета**: env, отдельный файл, secret manager API, launcher/proxy. Отдельно решаются шифрование, права и маскирование вывода.

Авторский вывод: `.env` не нужно обязательно заменять. Иногда достаточно валидировать env и перестать экспортировать секрет всем дочерним процессам. Иногда проблема — сложная структура, и тогда нужен структурированный конфиг.

## Форматы

| Вариант | Что даёт | Чего сам по себе не даёт |
|---|---|---|
| JSON + JSON Schema | Вложенные структуры, типы данных; schema задаёт ограничения | Комментарии в JSON; автоматическое наследование/env override; секретность |
| JSON5 | JSON с комментариями, trailing commas, удобными строками и именами ключей | Исполнение JS не является частью формата; схема и секретность отдельны |
| TOML | Типизированные значения, таблицы, массивы, комментарии; ориентирован на конфигурацию | Универсальная интерполяция/merge/приоритет env |
| YAML | Структуры, комментарии, anchors/aliases, теги | Безопасность любого loader; безопасное исполнение пользовательских тегов |
| JSONL | Независимое JSON-значение в каждой строке; удобен для потоков и логов | Единый объект конфигурации и правила merge; для обычного app config это обычно лишняя обвязка |

Источники: [JSON RFC 8259](https://www.rfc-editor.org/rfc/rfc8259), [JSON Schema](https://json-schema.org/overview/what-is-jsonschema), [JSON5 specification](https://spec.json5.org/), [TOML 1.1](https://toml.io/en/v1.1.0), [YAML 1.2.2](https://yaml.org/spec/1.2.2/), [JSON Lines](https://jsonlines.org/). Матрица назначения — авторская оценка, свойства форматов — по спецификациям. Поддержку конкретной версии TOML/YAML проверять в выбранной библиотеке.

JSON5 — не «JavaScript-файл с конфигом». Нельзя заменять парсер на eval. Конфиг `config.js` или `config.php` имеет другую модель доверия: это исполняемый код.

JSON Schema проверяет данные через validator; наличие файла schema рядом ещё ничего не валидирует. JSON5 можно сначала распарсить в модель данных, затем валидировать её; числа NaN/Infinity и прочие расширения требуют совместимости выбранного validator. [JSON5](https://spec.json5.org/), [JSON Schema](https://json-schema.org/overview/what-is-jsonschema).

## Если нужны наследование, вычисления и проверяемость

- **CUE** — язык/инструменты для определения, генерации и валидации данных. Интересен объединением ограничений и конфигурации. Это не просто «последний файл победил»: несовместимые ограничения могут дать ошибку. Для статьи — кандидат на сравнение с неявными overrides, не обязательная инфраструктура. [Introduction](https://cuelang.org/docs/introduction/).
- **Jsonnet** — язык генерации конфигов с функциями и композициями объектов; выдаёт JSON/YAML и другие форматы. Сокращает повторения, но требует этапа вычисления; не хранилище секретов. [Проект](https://jsonnet.org/).
- **Dhall** — типизированный конфигурационный язык с ограниченными эффектами и imports. Документирует integrity hashes и ограничения транзитивного доступа удалённых imports к локальным файлам/env. Это полезный пример того, как проектируют границу доверия; не обещание sandbox для приложения, потребляющего результат. [Safety Guarantees](https://docs.dhall-lang.org/discussions/Safety-guarantees.html).

Сложный конфиг не всегда выигрывает от языка генерации. Цена — ещё один инструмент, версия, обучение и диагностика. Для небольшого Symfony-приложения часто разумнее существующая конфигурация фреймворка + типы/валидация + явные file/env processors.

## Если хочется оставить env, но улучшить работу с секретами

- **SOPS** поддерживает шифрование файлов YAML, JSON, ENV, INI и binary; ключи через age/PGP или KMS. Это смена хранения, не обязательно формата. После расшифровки настоящий секрет снова доступен получателю. [Официальный README](https://github.com/getsops/sops/blob/main/README.rst).
- **dotenvx** оставляет KEY=value, умеет encrypted values; private key нужен отдельно, названия ключей и комментарии остаются видимыми. Не распространять лозунг «можно коммитить» на `.env.keys` или оставленные plaintext values. [Encrypted env file](https://dotenvx.com/docs/encrypted-env-file/).
- **dotenvx Envfile/redaction** задаёт правила видимости, типы и требования к шифрованию. README прямо предупреждает, что matching точный: преобразованные/производные значения не маскируются. Без Envfile или флага --redact вывод не редактируется. Это интересный готовый аналог части нашего предложения о контракте; нельзя называть эту идею новой. [README, Envfile redaction](https://github.com/dotenvx/dotenvx#readme), [Encryption policy](https://dotenvx.com/docs/envfile/encrypted/).
- **direnv** загружает/выгружает окружение по каталогу и требует разрешить `.envrc`. Но `.envrc` — Bash-код; подтверждение доверия не превращает его в пассивные данные. [Официальная документация](https://direnv.net/).
- **Secret file/API**: Compose secrets, systemd credentials, secret manager. Приложение читает файл/API вместо общего env. Подробные источники и границы — `secrets-research.md`.

Особенно важный нюанс dotenvx: наряду с encryption он документирует command substitution `$(...)`. Это возможность исполнения, а не криптографическая уязвимость. Перед загрузкой недоверенного файла выяснить, разрешён ли этот механизм в конкретном режиме/версии; в этом исследовании dotenvx не устанавливался и не исполнялся. [README, Command Substitution](https://github.com/dotenvx/dotenvx#readme).

## У форматов тоже есть неоднозначности

JSON RFC рекомендует уникальные имена в object и описывает различия поведения при дубликатах; Python json по умолчанию оставляет последнее значение. TOML запрещает повторное определение ключа. Поэтому «перейдём на JSON — приоритеты станут однозначными» слишком сильное обещание. Нужно задать политику дубликатов и merge отдельно. [RFC 8259 §4](https://www.rfc-editor.org/rfc/rfc8259#section-4), [Python json](https://docs.python.org/3/library/json.html#repeated-names-within-an-object), [TOML](https://toml.io/en/v1.1.0).

Локальный опыт `experiments/format-probe.py` проверяет JSON duplicates, отказ TOML и разницу Bash source/Node env-file на искусственном выражении. Уязвимые версии библиотек и эксплуатация CVE не запускались.

## Как использовать в статье

Не делать рейтинг «формат X безопаснее всех». Взять три сценария:

1. Несколько простых параметров: env + schema/typed validation, явный порядок источников.
2. Сложная вложенная конфигурация: JSON/TOML/YAML + schema, отдельно секреты.
3. Повторения между десятками сервисов: CUE/Jsonnet/Dhall как генерация/контракт; отдельно доставка credentials.

Сильный авторский эксперимент: одна настройка проходит файл → parse → merge → validate → runtime → safe diagnostic. Показать, какая конкретно ошибка исчезает после каждого решения и какую оно не устраняет.
