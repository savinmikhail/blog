# Уязвимости и эксплуатация конфигурации

Проверено по первичным источникам 16 октября 2026. Это датированная справка для [статьи](article.md), не актуальный security audit проектов пользователя. План статьи задаёт [outline.md](outline.md). Эксплуатация на реальных системах не выполнялась. Смена расширения файла сама по себе не устраняет риски доступа, загрузки или распространения секрета.

## 1. Публично доступный `.env`: реальная кампания, без CVE парсера

Unit 42 в августе 2024 описала инциденты с облачным вымогательством: публичные `.env` выдавали AWS credentials, которыми злоумышленники входили в аккаунты. Избыточные IAM-права позволяли расширить доступ. Исследователи наблюдали автоматический сбор файлов как минимум со 110 тысяч доменов. Число 230 миллионов относится к целям сканирования, а не к числу взломанных AWS-аккаунтов. Валидность всех найденных credentials исследователи не проверяли.

Для статьи: конфигурационный JSON или TOML, выставленный веб-сервером с ключами, имеет тот же класс проблемы. Хранить секреты вне document root, ограничивать выдачу статических файлов, использовать короткоживущие credentials и минимальные права; при раскрытии отзывать ключи.

Источник: [отчёт расследовавших инциденты Unit 42](https://unit42.paloaltonetworks.com/large-scale-cloud-extortion-operation/).

## 2. `source .env`: выполнение shell-кода, а не уязвимость dotenv

Bash исполняет команды из загружаемых shell-файлов. Поэтому загрузить неизвестный `.env` через `source` означает доверить ему исполнение, включая command substitution. Это другой режим обработки файла, чем обычный dotenv-парсер. Кроме того, `BASH_ENV` указывает файл, исполняемый перед неинтерактивным Bash; allowlist ключей важна при передаче окружения дочерним процессам.

Для статьи можно показать безопасный локальный опыт: значение, вычисленное через `printf`, вместо опасной команды. Не надо вводить принцип «любой dotenv запускает команды»: это неверно. Формат и конкретный загрузчик различаются.

Источник: [GNU Bash Startup Files](https://www.gnu.org/software/bash/manual/html_node/Bash-Startup-Files.html), [Bash manual](https://www.gnu.org/software/bash/manual/bash.html).

## 3. Node `--env-file`: данные могут управлять рантаймом

Документация Node прямо говорит: переменные настройки самого Node, включая `NODE_OPTIONS`, из `--env-file` применяются. Через `NODE_OPTIONS` разрешён preload модулей (`--require`, `--import`), хотя произвольные CLI-флаги не разрешены. Следовательно, недоверенный конфигурационный файл способен влиять на исполнение до прикладного кода. Это документированная функциональность, не CVE. Предпосылка: атакующий может подменить файл/переменную и загрузить доступный процессу модуль.

Нельзя автоматически переносить этот вывод на `dotenv.config()` внутри уже запущенного приложения: момент применения runtime options отличается. Для приложения лучше собирать конфигурационный объект из явного набора ключей, чем импортировать все неизвестные ключи в глобальное окружение.

Источник: [Node CLI, --env-file и NODE_OPTIONS](https://nodejs.org/api/cli.html#--env-filefile).

## 4. JSON5: конкретный дефект реализации

CVE-2022-46175 / GHSA-9c47-m6qq-7p4h: библиотека npm `json5` допускала влияние ключа `__proto__` на прототип объекта, возвращённого `JSON5.parse`. Уязвимы `<1.0.2` и `>=2.0.0,<2.2.2`; исправлены `1.0.2`, `2.2.2`. Важная граница: глобальный `Object.prototype` этим парсингом не изменялся. Последствия зависят от того, как приложение использует полученный объект.

Для статьи: это не доказательство, что JSON5 «по природе небезопасен», и не автоматическое RCE. Нужны актуальная библиотека, проверка ключей/схемы, аккуратное объединение объектов и запрет неожиданного наследования при чтении настроек.

Источник: [advisory сопровождающих JSON5](https://github.com/json5/json5/security/advisories/GHSA-9c47-m6qq-7p4h).

## 5. YAML: опасен выбранный API десериализации

PyYAML поддерживает конструирование Python-объектов и функции загрузки, способные выполнять Python-функции. Документация предупреждает о недоверенном вводе и предлагает `safe_load`, ограничивающий стандартными YAML-типами. У современных версий API и требования к Loader менялись; поэтому старый тезис «любой yaml.load сегодня автоматически RCE» некорректен. В статье указывать конкретный Loader и версию. `unsafe_load`/`UnsafeLoader` нельзя использовать для недоверенной конфигурации.

Проверка схемы и лимиты размера/глубины нужны отдельно: безопасное конструирование объектов не равно полной защите от исчерпания ресурсов. Последнее здесь архитектурная рекомендация, не утверждение о найденной текущей CVE.

Источник: [официальная документация PyYAML](https://pyyaml.org/wiki/PyYAMLDocumentation).

## 6. python-dotenv: запись файла тоже атакуемая операция

CVE-2026-28684 / GHSA-mf9w-mj56-hr94: при `set_key()`/`unset_key()` специально подготовленная символьная ссылка и перемещение temp-файла между файловыми системами могли приводить к перезаписи цели ссылки. Атакующему нужен доступ записи к каталогу `.env`; процесс должен иметь права записи на цель. Это локальная атака на rewrite, не выполнение кода при обычном `load_dotenv` и не проблема `find_dotenv`.

Advisory сопровождающих указывает affected `<1.2.1`, patched `1.2.2`: диапазон содержит несогласованность вокруг `1.2.1`, поэтому не делать вывод о безопасности этой промежуточной версии. Подтверждённая рекомендация источника — обновиться до `1.2.2` или применить указанный patch. Условия cross-device важны: нельзя заявлять, что любой вызов `set_key` эксплуатируем.

Источник: [advisory python-dotenv](https://github.com/theskumar/python-dotenv/security/advisories/GHSA-mf9w-mj56-hr94).

## Полезный вывод для структуры статьи

Разделить три уровня: (1) синтаксис и библиотека парсинга; (2) загрузчик, interpolation, merge и изменение глобального окружения; (3) доставка, права, секреты и наблюдаемость. Угроза в каждом случае требует своей предпосылки. Для своей демонстрации полезнее два безвредных опыта с shell/Node и разбор одной подтверждённой CVE, чем каталог страшных номеров.
