## Центральный тезис

Название-кандидат: **«Ваш .env — не конфигурационная система: кто побеждает, кто читает и где утекают секреты»**.

Полезность статьи для опытного разработчика — не в очередной структуре папок. Нужно показать путь одного значения: файл → парсер → интерполяция → контейнер → загрузчик приложения → диагностика/лог/агент. На каждом переходе меняются приоритет, представление и круг читателей. Организация файлов, маскирование, шифрование и ограничение доступа решают разные задачи.

## Проверено локально на искусственных данных

Скрипты и сырые результаты в `experiments/`. Контейнеры не запускались, production не затрагивался, реальные секреты не читались. Docker использовался только для локального `compose config`.

Версии: Node 26.10.0; Bash 5.2.37; GNU Make 3.81; Compose 2.38.2-desktop.1; Python 3.14.8. Вывод ограничен этими реализациями и версиями.

Один файл:

```dotenv
BASE=alpha
EXPANDED=${BASE}/data
LITERAL=cost$$cash
```

| Потребитель | EXPANDED | LITERAL |
|---|---|---|
| Node `--env-file` | `${BASE}/data` | `cost$$cash` |
| Bash `source` | `alpha/data` | `cost<PID>cash` |
| Make `include` + export | `alpha/data` | `cost$cash` |
| Compose `config --format json` | `alpha/data` | `cost$$cash` |

Последняя строка — сериализованная модель Compose, а не наблюдение внутри запущенного контейнера. Не делать из неё вывод о буквальном количестве `$` в runtime: Compose может экранировать доллар при выводе модели. Этот runtime-контроль оставлен следующим экспериментом.

Второй опыт: `--env-file base.env --env-file local.env`, service `env_file: runtime.env`, а `environment.VALUE: ${VALUE}`. Без VALUE в shell получено `local`, при VALUE=shell получено `shell`; независимый ONLY_RUNTIME из service env_file сохранился. Это пример двух стадий: сначала источник интерполяции, затем окружение сервиса.

Третий опыт: тестовый API_KEY задан через `environment`; `compose config --format json` вывел его открытым текстом. Тот же искусственный секрет как `secrets: file:` в секции definitions представлен путём без содержимого. Это не доказательство шифрования файла или недоступности Docker-администратору.

Четвёртый опыт: chmod 600 не мешает чтению владельцу файла. Следовательно, агент под тем же OS-пользователем не изолирован этим chmod от секретов.

## Приоритет — две разные таблицы

Официальные правила Compose: https://docs.docker.com/compose/how-tos/environment-variables/envvars-precedence/ и https://docs.docker.com/compose/how-tos/environment-variables/variable-interpolation/ .

В статье лучше нарисовать две стадии, а не переносить пятистрочную таблицу Compose на Symfony и shell. Host env и `.env` не означают автоматическое попадание переменной в контейнер. Порядок нескольких `--env-file`, environment/env_file, image ENV и runtime CLI — разные места разрешения значения.

Полезный пример: «Я поменял пароль в `.env.local`, а работает старый» — сначала проверить экспортированную shell-переменную и выбранные CLI-файлы, затем сформированную модель и контейнер, затем загрузчик/кэш приложения. Диагностика не должна печатать секрет: источник, имя и факт наличия часто полезнее значения.

## Конвенции и стандарты

Twelve-Factor — архитектурная рекомендация, не RFC синтаксиса dotenv: https://www.12factor.net/config . Она отделяет изменяемую по deploy конфигурацию от кода, рекомендует независимые env-настройки. Это не требование хранить все секреты в одном `.env` и не универсальная инструкция именовать `.env.prod.local`.

Проверку конкретных экосистем, спецификаций и альтернатив см. `ecosystems-research.md`. Не утверждать отсутствие стандарта для всех инструментов: некоторые реализации публикуют собственную грамматику. Не переносить Symfony-иерархию на Laravel, Node, Python, Spring и .NET без проверки загрузчика.

## Маскирование и LLM

Детали, источники и границы механизмов — `secrets-research.md`.

Редакционный стержень: секрет можно скрыть в интерфейсе и одновременно передать процессу открытым текстом. UI redact, CI masking, файловые permissions, шифрование at rest, grants конкретному сервису и sandbox агента нужно сравнивать отдельно.

Вместо обвинения «LLM постоянно сливают env» показать конкретные пути попадания данных: прямое чтение; диагностические команды `env`, `printenv`, `compose config`; дамп исключения; лог; файл с развёрнутым DSN; доступ агента к Docker/socket, runtime env или секрет-хранилищу. Проверять не только инструмент Read, но и shell/дочерние процессы. Если агент должен запускать приложение с секретом, нужен явно сформулированный доверенный launcher/proxy или ограниченная dev-учётка; один запрет на имя файла не доказывает изоляцию.

## Что в исходной заметке исправить

- «.env можно и нужно коммитить»: условный паттерн для несекретных defaults, не правило для любого проекта.
- «Laravel хуже»: заменить конкретным сравнением синхронизации example и runtime defaults; предпочтения не выдавать за технические дефекты.
- `.env.local.php`: проверить bootstrap и реальные env overrides, не обещать чтение только одного файла во всех режимах.
- `.env.prod.local` не объявлять ненужным: machine/deploy overrides и prod defaults имеют разные обязанности.
- `COMPOSE_ENV_FILES=...` в примере экспортировать, если рассчитываем передать дочерней команде.
- Разделив infra и app env, показать, как POSTGRES_* реально достигают парсера DATABASE_URL. Файлы из разных директорий сами друг друга не наследуют.
- Make include не назвать dotenv-loader: это исполнение make-синтаксиса. Shell source тоже выполняет код. Конфиг из недоверенного источника нельзя считать безопасным текстом.
- Не выводить сгенерированные реальные ключи в статье/CI/LLM. Использовать явно синтетические значения.
- Блокировка placeholder — полезный guard, но не проверка энтропии, актуальности, scope или отзыва ключа.
- Env processors — преобразования и загрузка значений, не полноценная валидационная схема всего конфига.
- Secret scanner не доказывает отсутствие секретов. Сканирование, маскирование и предотвращение чтения — разные контроли.

Полные тексты двух публикаций также просмотрены:

- В статье 872128 перечислены env, Swarm, BuildKit и Vault. Есть конкретная неточность: раздел Compose утверждает отсутствие обычных Compose secrets и смешивает их с BuildKit/экспериментальными возможностями. Актуальная официальная документация описывает file-based Compose secrets отдельно: https://docs.docker.com/compose/how-tos/use-secrets/ . В нашем материале стоит аккуратно развести build/runtime и Compose/Swarm, без обобщения о качестве всей публикации.
- В статье Яндекс Практикума 801047 уже есть разделение prod/test/CI/local/personal, TTL, сессионная выдача и доставка из хранилища. Само предложение «не хранить всё в одном файле» слабее этого материала. Наш прикладной вклад — воспроизводимая цепочка override, различия парсеров и безопасная диагностика для работы с агентом.

Остальные ссылки выше — навигационная выборка; полнота их содержания пока не проверена.

Предлагаемый вклад автора: единая проверяемая цепочка одного значения, runnable parser comparison, два разных приоритета Compose, матрица «где скрыто / кто способен прочитать», реальный PHP/Symfony кейс и threat model агента. Не продавать тему как неизвестное открытие.

## Структура будущей статьи

1. Короткий кейс: настройки правильные на диске, но процесс видит другое; второй кейс — диагностика раскрыла ключ.
2. Четыре парсера одного файла: результаты и минимальный репозиторий для повторения.
3. Две стадии Compose и дальнейшая загрузка Symfony: проследить одну переменную.
4. Разделить defaults, deployment overrides и secrets; обосновать, что коммитим.
5. ConfigMap/Secret, Compose secrets и файловая доставка: решаемые задачи и границы.
6. Маскирование в программах/CI против реальных прав доступа, затем AI-agent как ещё один читатель.
7. Практический контракт конфигурации: имя, тип, обязательность, источник, секретность, потребитель, правило обновления, безопасная диагностика.
8. Минимальный план миграции без обязательного внедрения Vault: inventory → safe defaults → per-service grants → schema → production guards → безопасная диагностика → проверка доступа агента.

## Следующая валидация перед написанием

- Запустить daemon-backed runtime опыт с fake secret, сравнить config и inspect; не писать, что он уже выполнен.
- Выполнить одинаковые fixtures через реальные Symfony Dotenv/python-dotenv, версионировать результаты.
- На Linux под отдельным UID проверить доступ к mounted file и процессному env. macOS same-user опыт не доказывает поведение Kubernetes.
- Проверить негативные примеры агентов в изолированной среде без настоящих ключей: direct read, shell cat, дочерний процесс, diagnostic dump. Не использовать облачный запрос с production secret.
- Проверить обновление env-secret против volume-secret и чтение приложения, прежде чем обещать автоматическую ротацию.
- Сопоставить каждый публичный пример с исходником и убрать абсолютные приватные пути/реальные credentials.
