# Секреты, маскирование и LLM: исследовательская записка

Проверено по первичным источникам 2026-10-16. Это исследование для статьи, не инструкция менять существующие проекты. Эксперименты ниже предложены, но не проведены. Реальные секреты не использовались.

## Главный редакционный вывод

Полезнее статьи «не коммитьте .env» будет материал о четырёх разных операциях: хранить секрет, доставить процессу, ограничить читателей, убрать из диагностического вывода. Разделение файлов решает организацию; отдельная граница доступа решает чтение; маскирование решает некоторые каналы вывода. Из одного автоматически не следует другое. Это авторский синтез источников ниже.

## Docker Compose: файл вместо переменной — конкретный механизм, не магическое шифрование

Compose secrets выдаются только явно указанным сервисам и монтируются файлами в `/run/secrets/<name>`. Для обычного Compose доставка использует bind mount исходного файла. Это не обещание шифрования исходника на хосте. Docker отдельно предупреждает о попадании env в отладочные логи. `_FILE` — соглашение некоторых образов (например MySQL/Postgres), а не универсальная функция всех приложений: код должен уметь читать файл. [Официальный how-to](https://docs.docker.com/compose/how-tos/use-secrets/).

Важно для практического примера: актуальный reference говорит, что `uid`, `gid`, `mode` поддерживаются Compose для secrets с источником `environment`, но для источника `file` игнорируются из-за bind mount. Нельзя обещать ограничение прав только потому, что в YAML записано `mode: 0400`. Проверять фактические права внутри контейнера, владельца исходника и пользователя приложения. [Services reference, secrets](https://docs.docker.com/reference/compose-file/services/).

`docker compose config --environment` намеренно выводит окружение интерполяции. Обычный `config` разрешает конфигурацию; предусмотрены `--no-env-resolution` и `--no-interpolate`. Они полезны для конкретных задач диагностики, но не являются универсальным scrubber: секрет может быть записан литералом в YAML. [CLI reference](https://docs.docker.com/reference/cli/docker/compose/config/).

Нельзя переносить обещания Swarm на Compose: Swarm описывает иной жизненный цикл, защищённую доставку и in-memory secret mounts. В статье явно писать, какой режим показан. [Swarm secrets](https://docs.docker.com/engine/swarm/secrets/).

## Kubernetes: разделение модели данных уже стандартное, безопасность требует настройки

ConfigMap предназначен для конфигурации, Secret — конфиденциальных данных. По умолчанию данные Secret в etcd не зашифрованы; base64 — кодировка. У mounted Secret kubelet использует tmpfs и удаляет локальную копию после удаления нуждающегося Pod. Пользователь, который может создавать Pods/Deployments в namespace, способен получить косвенный доступ к его Secrets; одного запрета `get secrets` недостаточно. Privileged-контейнеры могут читать Secrets на узле. Это хороший контрпример тезису «назвали объект Secret — защищено». [Secrets](https://kubernetes.io/docs/concepts/configuration/secret/), [good practices](https://kubernetes.io/docs/concepts/security/secrets-good-practices/).

Шифрование at rest включается отдельно конфигурацией API server; первый `identity` provider означает отсутствие защиты конфиденциальности. При включении шифрования существующие записи нужно переписать, простой restart не перешифровывает всю историю. RBAC и шифрование решают разные угрозы. [Encryption at rest](https://kubernetes.io/docs/tasks/administer-cluster/encrypt-data/).

## CI: звёздочки в логе не ограничивают исполняемый код

GitHub redaction в большой степени опирается на совпадение значения. Документация рекомендует отдельные секреты вместо одного JSON/XML/YAML blob и регистрацию новых чувствительных производных значений (например созданного JWT) для redaction. При утечке нужно удалить лог и ротировать секрет. `::add-mask::VALUE` полезен для значений, не объявленных GitHub secrets. [Secure use](https://docs.github.com/en/actions/reference/security/secure-use), [secrets reference](https://docs.github.com/en/actions/reference/security/secrets).

GitLab прямо предупреждает: masked/protected variables не спасают от вредоносного скрипта, который отправляет значение наружу. File variables передают через env путь к временным файлам, поэтому обычный `env` не печатает само содержимое; доступный скрипту файл всё равно читаем. Masking, protection по веткам и external secrets решают разные задачи. [CI/CD variables](https://docs.gitlab.com/ci/variables/).

## systemd: не всем сервисам вообще стоит отдавать секрет через env

Первичный manpage systemd предупреждает: переменные unit доступны через D-Bus и распространяются по дереву процессов. Для секретов предусмотрены `LoadCredential=`, `LoadCredentialEncrypted=`, `SetCredentialEncrypted=`. Credential доставляется файлом в read-only расположении, доступном пользователю unit и root; по возможности память не swap-ится. `$CREDENTIALS_DIRECTORY` содержит путь, не значение. Это удачный пример из другой экосистемы: приложение получает интерфейс чтения секрета, а не гигантский общий env. [Исходник manpage systemd.exec](https://github.com/systemd/systemd/blob/main/man/systemd.exec.xml).

## LLM: доступ агента надо рассматривать по каналам

Не подтверждено этим исследованием, что «утечки происходят постоянно»: для такого количественного заявления нужны отдельные данные. Более честный заход: диагностические команды и агентные инструменты добавляют места, куда может попасть секрет.

Claude Code `Read` deny ограничивает встроенные файловые инструменты и распознаваемые файловые shell-команды. Документация отдельно предупреждает, что произвольный Python/Node subprocess может читать файлы косвенно, а рекурсивный grep без имени конкретного файла не покрывается таким правилом. Для этого требуется OS sandbox. `.claudeignore` не действует. [Permissions](https://code.claude.com/docs/en/permissions).

В актуальной документации Claude Code sandbox охватывает shell, но не MCP, hooks и built-in file tools. По умолчанию чтение широко разрешено, env наследуется. Есть `sandbox.credentials` deny для файлов/переменных и mask через sentinel с подстановкой настоящего значения прокси только при исходящем запросе. Маскирование требует TLS termination, разрешённых hosts и trusted settings; на macOS credential files блокируются вместо masking. Это существенно отличается от замены токена на звёздочки после печати. Перед примером проверить версию: функции быстро меняются. [Sandboxing](https://code.claude.com/docs/en/sandboxing).

Codex read-only — ограничение записи, а не обещание скрыть секреты. Документация показывает отдельные политики сети, sandbox и approval. Не нужно называть read-only безопасным для конфиденциальности автоматически. Путь `/codex/security/` ныне ведёт к другому продукту Codex Security; для агентных прав использовать страницу approvals. [Agent approvals and security](https://learn.chatgpt.com/docs/agent-approvals-security).

Практический вывод автора: `chmod 600` ограничивает других пользователей, но агент, запущенный от владельца файла, сохраняет право читать. Поэтому тестировать границу на отдельном пользователе/контейнере/VM или sandbox deny-read. `.gitignore`, отсутствие файла в поиске IDE и просьба в AGENTS.md сами по себе не OS-права. Контейнер тоже не изоляция, если ему смонтирован домашний каталог или Docker socket. Эти выводы — модель угроз, не заявленная гарантия конкретного продукта.

## Эксперименты, которые дадут статье собственную ценность

Все значения синтетические (`DEMO_SECRET_DO_NOT_USE_123`), отдельный fixture repo, никаких prod `.env` и внешней отправки.

1. **Куда доезжает одно значение.** Два контейнера: env и secret file. Проверить resolved Compose config, interpolation environment, container inspect, `env`, диагностический exception и log. В отчёте таблица «есть значение / есть путь / отсутствует» с точной версией Docker и ОС. Не обещать заранее результаты inspect: запустить и сохранить артефакты.
2. **Права против идентичности.** Файл 0600: чтение владельцем, отдельным UID, приложением, агентом от владельца. Показать, что меняет deny-read sandbox. Проверить file-based secrets: совпадают ли фактические права с YAML mode.
3. **Deny Read против subprocess.** На dummy-файле проверить built-in Read, cat, recursive grep, Python open и подключённый MCP. Не искать обходы ради реальных секретов: цель сравнить покрытие официально заявленных границ.
4. **Редакторская диагностика.** Две команды: обычный дамп config и санитизированный отчёт с именем ключа, источником/приоритетом, типом, флагом sensitive и `is_set`, без значения. Именно такой контракт даст читателю полезный инструмент сверх справочника.
5. **Masking производных значений.** В тестовом CI вывести dummy secret как есть, как часть JSON, encoded и derived token. Задокументировать фактические результаты; не трактовать отсутствие одной формы в логе как невозможность кражи.

Самая сильная связка статьи: «хочу объяснить агенту сломанный DATABASE_URL, но не отдавать пароль» → показать происхождение итогового значения и безопасную диагностику → сравнить с файлами/credentials и реальной изоляцией. Приложение всё равно нуждается в настоящем секрете; значит надо определять, кто может запускать его и наблюдать вывод.
